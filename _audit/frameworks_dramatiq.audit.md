FIX-CRITICAL: the retry-exhaustion prose and `DeadLetterMiddleware` use `after_skip_message`, but Dramatiq emits that hook only when processing raises `SkipMessage`; the `Retries` middleware exhausts retries by calling `message.fail()` in `after_process_message`, so the promised alert/copy hook never runs — use `on_retry_exhausted` or a correctly filtered nack/failure hook. Source: https://raw.githubusercontent.com/Bogdanp/dramatiq/v2.2.0/dramatiq/middleware/retries.py and https://raw.githubusercontent.com/Bogdanp/dramatiq/v2.2.0/dramatiq/worker.py, checked 2026-08-03.
FIX-HIGH: the `on_retry_exhausted="alert_ops"` actor accepts one argument, but Dramatiq sends two: the failed message dictionary and a retry metadata dictionary — change the callback signature and show both payloads, otherwise the alert actor itself fails when the original actor exhausts retries. Source: https://raw.githubusercontent.com/Bogdanp/dramatiq/v2.2.0/dramatiq/middleware/retries.py, checked 2026-08-03.
FIX-HIGH: the worker success signal promises an INFO line naming every consumed queue, but Dramatiq 2.2 logs only the main boot line and "Worker process is ready for action" at INFO; consumer creation is DEBUG and has no quoted "Consumer for queue ... is ready" line — replace the fabricated log with actual output and use broker queue inspection or DEBUG startup logs to verify queue binding. Source: https://raw.githubusercontent.com/Bogdanp/dramatiq/v2.2.0/dramatiq/cli.py and https://raw.githubusercontent.com/Bogdanp/dramatiq/v2.2.0/dramatiq/worker.py, checked 2026-08-03.
FIX-HIGH: "Actor Composition" publishes four independent messages sequentially under "Patterns worth copying" — a crash after any send creates a permanently partial onboarding flow; label it best-effort fan-out or replace it with a transactionally persisted set of intents/outbox rows plus per-effect idempotency.
FIX-HIGH: "Database-backed dedup keys" keeps a database transaction open across the Stripe call and commits no intent before the external effect — replace it with the intent-first, request-hash-checked operation record from the general reliability note, then send the same stable key to the provider and persist its operation ID/result.
FIX-MED: the note has no broker security boundary despite treating Redis/RabbitMQ as a task dispatch path — add private networking, authentication/TLS, least-privilege credentials, payload minimization, and the consequence that broker write access can invoke any registered actor with attacker-chosen arguments.
FIX-MED: the DLQ replay loop republishes every stored message but records neither an operator action nor that an ID was redriven, so rerunning the script duplicates the replay — require an explicit selected-ID set, preserve the business idempotency key, and record the redrive before enqueueing.
FIX-LOW: "Two strategies" introduces a list numbered 1, 2, and 3 — change the count to three.

FIX-CRITICAL: "Permanent failures need an alert" repeats the non-firing `after_skip_message` hook for retry exhaustion — replace it with an `on_retry_exhausted` actor accepting `(message_data, retry_data)` and test that the alert fires after the configured retry count. Source: https://raw.githubusercontent.com/Bogdanp/dramatiq/v2.2.0/dramatiq/middleware/retries.py and https://raw.githubusercontent.com/Bogdanp/dramatiq/v2.2.0/dramatiq/worker.py, checked 2026-08-03.
FIX-HIGH: the note promises durable submission but never implements its outbox — replace the two-write `db.create_job(); process_document.send()` canonical path with a transaction that creates job plus outbox, a confirmed publisher, and an actor that claims by expected state/version and stable attempt token.
FIX-HIGH: the canonical actor unconditionally writes `processing`, writes `failed`, and re-raises for Dramatiq retry — show how a retry moves from retryable failure back to an owned attempt without status flapping, how duplicate delivery loses the conditional claim, and how completion verifies the same lease/attempt token.
FIX-HIGH: the integration test asserts `data["status"] == "queued"`, but the canonical `start_processing()` response contains only `{"job_id": job_id}` — make the canonical endpoint and test use one contract.
FIX-HIGH: both files claim healthy workers print one INFO consumer line per queue, but Dramatiq 2.2 emits no such INFO line — use the actual main/worker-ready logs and a broker/DEBUG-level queue-binding check. Source: https://raw.githubusercontent.com/Bogdanp/dramatiq/v2.2.0/dramatiq/cli.py and https://raw.githubusercontent.com/Bogdanp/dramatiq/v2.2.0/dramatiq/worker.py, checked 2026-08-03.
FIX-HIGH: the heartbeat-file liveness example says to check freshness but the supplied probe only runs `test -f`, so a file touched once at boot remains healthy forever while consumer threads are wedged — implement an mtime threshold updated by an independent heartbeat loop, and do not use task completion as runtime liveness.
FIX-HIGH: the examples set actor `time_limit=300_000` and then configure only `stop_grace_period: 60s` while instructing readers to place grace above the worst-case task duration — align the numbers or demonstrate checkpoint/requeue behavior before the container's forced kill.
FIX-MED: "Redis databases 0-15 are cheap isolation" is not portable to Redis Cluster, which supports only database 0, and separate DB numbers are not a security boundary — describe key-prefix/logical isolation and use separate instances/ACLs when isolation matters.
FIX-MED: the test fixture rebinds actor brokers but does not rebind the module-level `db` used by the real actor — monkeypatch `myapp.tasks.db` to the test repository so the assertion proves the actor changed the fixture's row.
FIX-MED: the deployment section omits Dramatiq's documented pre-fork boundary — warn that builtin broker clients are not process-safe when a web server forks after importing them, and initialize the broker after fork or avoid preload. Source: https://dramatiq.io/troubleshooting.html, checked 2026-08-03.
