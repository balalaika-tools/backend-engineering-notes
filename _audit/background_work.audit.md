# background_work/05_production_reliability_patterns.md
Summary: 2 critical, 4 high, 1 med, 0 low

FIX-CRITICAL: §3 calls `lease_owner` a fence but the same worker ID can be reused across process restarts or later attempts, so an old partitioned process can renew or complete a newer attempt with the same owner value — generate a unique lease/attempt token on every claim and include it in heartbeat, completion, failure, and reconciliation predicates; `worker_id` remains observability metadata, not the fencing value.
FIX-CRITICAL: §4 stores `request_hash` but never compares it when an idempotency key already exists, so reusing a key with a different payment amount can return the first operation's response as if it belonged to the new request — compare the persisted hash before every reuse and reject a mismatched key as a conflict before reading or calling the provider.
FIX-HIGH: §3 introduces leases and then moves too quickly into SQL for a reader learning the pattern — build the mechanism from the failure first: show a worker claiming a job, crashing after `RUNNING`, and leaving permanent ownership when only a lock/status flag exists; contrast that with a timestamped lease that another worker may reclaim after expiry. Explicitly state that a lease recovers abandoned execution but does not make an external side effect exactly once, which is why the same workflow still needs idempotency. Finish with one failure-injection test that pauses the first worker past expiry and proves only the current token can commit.
FIX-HIGH: §4 contains the parts of idempotency but not a single decision path that teaches why and where to apply them — begin with the ambiguous-crash timeline `provider accepted effect → worker died before durable completion → queue redelivered`, then distinguish transport deduplication, business-effect idempotency, and the unrealistic promise of end-to-end exactly-once execution.
