# fundamentals/fastapi/09_background_tasks_and_routers.md
Summary: 1 critical, 6 high, 8 med, 4 low

FIX-CRITICAL: The section-1 gotcha "No error reporting to the client. Log inside the task; failures do not propagate." is factually wrong and leaves the reader with an isolated-tasks model — an exception in a background task does propagate up the ASGI stack, and it aborts every task queued after it on the same response; reproduced on FastAPI 0.141.1 / Starlette 1.3.1 with two tasks added via `add_task` where the first raises, the second never executed, the client still received `200`, and a registered `@app.exception_handler(Exception)` did not catch it because the response had already started. Replace the bullet with: tasks in one `BackgroundTasks` chain run sequentially and the first exception ends the chain, so wrap each task body in its own `try/except` if later tasks must still run. Source: https://github.com/encode/starlette/blob/master/starlette/background.py, checked 2026-08-03.

FIX-HIGH: Section 1 never tells the reader how to observe that a background task actually fired — add the success signal and the tell for the silent failure: on success the task's own log line appears in the server log after uvicorn's `"POST /signup HTTP/1.1" 200 OK` access line; on failure uvicorn prints `ERROR: Exception in ASGI application` with a traceback whose tail is `starlette/responses.py ... await self.background()` then `starlette/background.py ... await task()`, and the client's 200 is unchanged either way, so a task that never fired leaves no client-visible trace at all. Verified FastAPI 0.141.1 / Starlette 1.3.1, checked 2026-08-03.

FIX-HIGH: The `custom_openapi()` snippet's line `schema["components"]["securitySchemes"] = {...}` raises `KeyError: 'components'` when copied into an app that has no Pydantic models and no security dependencies — `get_openapi()` only emits the key conditionally (`if components: output["components"] = components`), and an app documenting an API-key header that is deliberately *not* a FastAPI security dependency is exactly that case; change the line to `schema.setdefault("components", {})["securitySchemes"] = {...}`. Reproduced on fastapi 0.141.1. Source: https://github.com/fastapi/fastapi/blob/master/fastapi/openapi/utils.py, checked 2026-08-03.

FIX-HIGH: The section-3 per-endpoint metadata table has 7 rows (`summary`, `description`, `response_description`, `operation_id`, `tags`, `deprecated=True`, `include_in_schema=False`) with no marked default subset — bold `summary`, `tags`, and `include_in_schema` and precede the table with a line naming those three as the ones a reader will actually reach for; the "one marked entry shown in use" requirement is already satisfied by the `/healthz` `include_in_schema=False` example.

FIX-HIGH: Section 2 carries no failure-mode coverage at all — add the two that bite first: (a) route declaration order is load-bearing, and declaring `@router.get("/{user_id}")` before `@router.get("/me")` makes `GET /users/me` return `422` with `{"type":"int_parsing","loc":["path","user_id"],"input":"me"}` because the parameterised route matches first — the note's own `users.py` happens to be in the correct order but never says the order matters; (b) a prefix ending in `/` raises `AssertionError: A path prefix must not end with '/', as the routes will start with '/'` at import time, from both `APIRouter(prefix=...)` and `include_router(prefix=...)`. Verified FastAPI 0.141.1, checked 2026-08-03.

FIX-HIGH: The `main.py` line `app.include_router(admin.router, prefix="/admin")   # prefix can also be added here` is a trap sitting next to a structure diagram that labels `admin.py` as "APIRouter for /admin" — if `admin.py` sets `prefix="/admin"` on its `APIRouter(...)` the way the note's own `users.py` does, the two prefixes concatenate to `/admin/admin/ping` and every `/admin/...` request 404s; change the comment to state the prefix belongs in exactly one of the two places, and give the tell (the doubled path appears in `/docs` and in `app.openapi()["paths"]`). Verified FastAPI 0.141.1, checked 2026-08-03.

FIX-HIGH: The error-path workaround `JSONResponse(..., background=task)` is not implementable as written — `task` is never defined, the import is missing, and the tasks the endpoint already added are unreachable from the handler; show the full form (`from starlette.background import BackgroundTask`, then `return JSONResponse({...}, status_code=500, background=BackgroundTask(send_welcome_email, email, name))`) and state that the handler must reconstruct the task with its own arguments (e.g. stash them on `request.state` in the endpoint) because the endpoint's `BackgroundTasks` object is discarded along with the aborted response, and that this only covers exception types you actually register a handler for. Verified on FastAPI 0.141.1 / Starlette 1.3.1: the handler-attached task ran, the endpoint-attached task did not. Checked 2026-08-03.

FIX-MED: Section 1 asserts three consequences separately (runs after the response, dies if the endpoint raises, occupies the worker) before revealing the one mechanism that generates all three — move the mechanism to the front of the section: Starlette attaches the task list to the `Response` object and `Response.__call__` awaits `self.background()` after the body has been sent, so no response object means no tasks and the request's ASGI call is not finished until the tasks are. Right now the mechanism is buried mid-bullet in "Gotchas" at "Background tasks are attached to the response object", after the facts it explains.

FIX-MED: The "Fire-and-Forget" framing in the section-1 header plants a specific wrong model the note never kills — that the request is over and the task runs independently of it. Add the contrast explicitly: the response bytes are gone, but the ASGI call for that request is still in flight until the tasks finish, which is why a task's exception is reported against that request and why a slow task keeps occupying the worker.

FIX-MED: "Use `async def` tasks for I/O, sync `def` for CPU" is misleading and contradicts the bullet directly above it — sync tasks are dispatched to anyio's default thread limiter (40 threads) and CPU-bound Python in a worker thread still holds the GIL, so routing CPU work through `def` does not keep the event loop free. Rewrite as: use `async def` for I/O; for genuinely CPU-bound work use neither and move it to a process pool or a real queue; and note that more than 40 concurrent sync tasks queue behind the limiter. Source: https://anyio.readthedocs.io/en/stable/threads.html, checked 2026-08-03.

FIX-MED: The versioning bullet says "Don't try to serve v1 and v2 from the same FastAPI instance — use two instances on two paths" with no mechanism and no reason, and it contradicts the same bullet's own alternative of including routers under a v1 prefix (which is serving a version from one instance) — give the mechanism (`app.mount("/v2", v2_app)`) and the actual reason to prefer it: each mounted sub-application gets its own independent OpenAPI schema and its own `/docs`, and FastAPI sets the sub-app's `root_path` automatically so its docs UI resolves. Source: https://fastapi.tiangolo.com/advanced/sub-applications/, checked 2026-08-03.

FIX-MED: The `operation_id` table row warns that changing it breaks client SDKs but omits the constraint that actually bites — `operation_id` must be unique across the entire app or the emitted spec is invalid and codegen collides; add that, plus `FastAPI(generate_unique_id_function=...)` as the way to set them app-wide instead of one endpoint at a time (with its own caveat that every path-operation function name must then be unique across modules). Source: https://fastapi.tiangolo.com/advanced/path-operation-advanced-configuration/, checked 2026-08-03.

FIX-MED: The `custom_openapi()` section ships an instruction with no success signal — add that a working override shows `curl localhost:8000/openapi.json | jq .components.securitySchemes` returning the `ApiKey` block and an Authorize entry in `/docs`, and name the silent failure: because the function returns early on a populated `app.openapi_schema`, if anything called `app.openapi()` or hit `/docs` before `app.openapi = custom_openapi` was assigned, the cached un-customised schema is served from then on with no error anywhere.

FIX-MED: Add that injecting `securitySchemes` into the OpenAPI schema is documentation only — nothing in the app validates `X-API-Key` as a result, and `/docs` will render an Authorize box for a scheme that is not enforced; without this a reader can finish the section believing the endpoint is now protected.

FIX-MED: `routers/users.py` declares `get_current_user` twice — once in the router-level `dependencies=[Depends(get_current_user)]` and again as `user = Depends(get_current_user)` in `/me`'s signature — which reads as contradicting the note's own "Put the auth dependency at the router level, not on every route" advice 30 lines later; explain that the router-level entry enforces it while the signature form is how you obtain the *value*, and that per-request dependency caching means the function still executes exactly once (verified: one call per request on FastAPI 0.141.1, checked 2026-08-03).

FIX-LOW: The note carries no `> **Key insight**:` line anywhere — add exactly one, in section 1: `BackgroundTasks` is not a queue with one worker, it is a callback bolted onto a response object, so its reliability is exactly the reliability of that response getting built and sent — which is why every one of its failure modes is a response that never happened.

FIX-LOW: Section headers label their topic instead of stating what the reader leaves with — rewrite them as claims across the whole file, e.g. "Gotchas" → "Four ways a background task silently never runs", "Sensible patterns" → "Where the prefix, the tag, and the auth dependency belong", "2. `APIRouter` — Organizing a Larger App" → "2. `APIRouter` — one prefix, one tag, one auth dependency per domain". Source: https://fastapi.tiangolo.com/tutorial/path-operation-configuration/, checked 2026-08-03.
